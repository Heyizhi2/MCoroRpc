# 第四章 协程库的设计与实现

## 4.1 设计目标

本框架选择自行实现协程库而非直接使用现有方案（如Boost.Coroutine2或libco），主要出于以下考量：其一，自主实现能够将协程调度与上层网络框架深度整合，使协程生命周期管理与事件循环紧密耦合；其二，C++20标准仅提供底层语言机制，缺少可直接使用的高层抽象，自建协程库可以提供统一的返回类型和调度接口，简化上层开发；其三，针对远程过程调用场景设计，可以对协程取消、超时控制等特性进行针对性优化。

协程库的核心设计目标是实现协程生命周期的完全可控、协程状态的可观测性，以及协程间的高效通信能力。

## 4.2 Task与协程链机制

协程函数必须返回一个包含promise_type类型的对象。本框架设计了Task<R>作为协程的统一返回类型，其内部持有协程句柄，并通过移动语义管理所有权。当Task对象销毁时，协程句柄自动析构，实现了资源获取即初始化的资源管理模式。

Promise<R>是协程返回对象的内部实现，继承自CoroHandle基类和TaskResult<R>结果存储类。CoroHandle基类提供协程调度功能，TaskResult<R>则使用variant类型存储协程结果，支持正常返回值、异常或空状态三种情况。

**协程链机制**是本框架的关键设计。子协程执行完毕后，需要自动恢复父协程的执行，这通过重写final_suspend()方法实现。当协程执行结束时，C++运行时会调用final_suspend()，返回一个自定义的等待器。在等待器的suspend方法中，检查当前协程是否存在父协程；若存在，则将父协程重新加入事件循环的就绪队列，等待下次调度执行。

```
┌─────────────────────────────────────────────────────────────────────┐
│                         协程链调度流程                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   父协程                      子协程                                 │
│      │                          │                                    │
│      │ 调用子协程                │                                    │
│      │─────────────────────────→│ 创建并开始执行                      │
│      │                          │                                    │
│      │ co_await 挂起            │ 执行中...                          │
│      │ ◄────────────────────────│                                    │
│      │                          │                                    │
│      │                 ┌────────┴────────┐                          │
│      │                 │  执行完毕        │                          │
│      │                 │  final_suspend()│                          │
│      │                 └────────┬────────┘                          │
│      │                          │                                    │
│      │ 检查并恢复父协程           │                                    │
│      │                          │                                    │
│      │ 重新加入就绪队列           │                                    │
│      │ ◄────────────────────────│                                    │
│      │                          │                                    │
└─────────────────────────────────────────────────────────────────────┘
```

这种设计将协程链的调度责任完全交给事件循环，避免了手动维护协程间调用关系的复杂性。同时，由于父协程的恢复发生在事件循环层面而非子协程内部，因此父协程不会立即执行，而是与其他就绪协程公平竞争调度资源。

值得注意的是，协程链与函数调用有本质区别：函数调用是同步的，调用者必须等待被调用者返回；协程链是异步的，子协程挂起时父协程可以释放执行权，父子协程可以交错执行。这种设计契合异步I/O场景，使得等待网络响应时可以让出执行权。

## 4.3 协程状态管理

协程在生命周期内经历多种状态，理解这些状态及其转换规则是理解整个调度系统的关键。

本框架定义了四种互斥状态：未调度状态表示协程刚创建尚未加入调度队列；就绪状态表示协程已在调度器的就绪队列中等待执行；挂起状态表示协程因等待I/O、定时器或其他协程而暂停执行；取消状态表示协程被显式终止。

状态转换遵循以下规则：协程创建后处于未调度状态，调用调度方法后转为就绪状态；协程执行过程中遇到co_await操作时转为挂起状态，等待条件满足后重新转为就绪状态；就绪协程被事件循环选中后开始执行，执行完毕后进入最终挂起点；任何状态下均可调用取消方法转为取消状态。

Handle基类为所有协程提供唯一标识符生成器和状态管理接口。标识符通过原子计数器生成，确保在多线程环境下的唯一性。状态修改操作本身不是原子的，但由于事件循环通常在单线程运行，实际不存在状态竞争问题。

这种状态设计借鉴了操作系统进程状态的思想，但做了简化：只保留了对协程调度有意义的状态，省略了创建态、终止态等不常用状态。

## 4.4 事件循环调度器

事件循环是协程运行时的核心引擎，负责决定哪个协程在何时执行。本框架的事件循环借鉴了计算机网络领域经典的事件驱动编程模型，但针对协程特点进行了调整。

**就绪队列**采用FIFO队列实现，存储等待执行的协程标识。选择队列而非栈或优先级队列的原因在于：协程应该按照先到先服务的原则公平执行，优先级调度在本框架的应用场景（网络服务器）中并非必要。

**定时器管理**采用最小堆数据结构，按超时时间排序。相比有序链表，最小堆在插入和删除操作上的对数时间复杂度更优；相比平衡二叉树，实现更简单且缓存友好；相比层级桶，最小堆不依赖时间精度假设。本框架的应用场景中，定时器数量通常与活跃协程数量相当（在几百到几千量级），最小堆的性能表现足够。

**与epoll的交互**是本框架区别于其他协程库的关键点。Linux的epoll机制提供了高效的事件多路复用能力，但它是基于回调而非协程的。本框架通过等待器将epoll事件转换为协程挂起：当协程执行网络I/O操作时，对应的等待器向事件循环注册监听事件并挂起协程；事件循环在epoll_wait返回可读/可写事件时，将对应协程重新加入就绪队列。

这种设计的好处在于：大量并发连接可以共享少量线程资源，每个连接在等待I/O期间不占用任何线程栈空间；代码风格保持同步形式，避免了回调地狱。

事件循环的执行流程并非严格按"先处理定时器再处理I/O事件"的顺序，而是根据就绪队列的状态动态调整。如果就绪队列非空，说明已有协程等待执行，此时应尽快处理这些协程而非等待I/O；如果就绪队列为空，则让epoll_wait适当等待，直到有I/O事件发生或定时器到期。这种设计保证了低延迟响应。

**设计局限**：当前事件循环采用单线程模型，无法利用多核处理器并行执行多个协程。这对于计算密集型场景是不利的，但在网络I/O密集场景中，单线程模型的性能损失并不明显，因为瓶颈通常在I/O等待而非CPU计算。未来的改进方向是支持多事件循环并行运行，每个事件循环绑定到独立线程。

## 4.5 异步I/O机制

异步I/O是连接协程与操作系统I/O子系统的桥梁。本框架的I/O等待器实现遵循可等待对象协议，使协程能够以同步代码风格执行异步操作。

等待器定义三个方法：await_ready方法返回false，表示协程必须等待；await_suspend方法向事件循环注册I/O监听并挂起协程；await_resume方法在I/O事件触发后返回值并继续执行后续逻辑。

读写等待器是该机制的两个实现。当协程执行读操作而数据尚未到达时，读等待器将协程挂起；数据到达后，事件循环唤醒协程继续执行。写等待器同理，只是监听可写事件。

**资源获取即初始化模式**在等待器中的应用是保证资源正确释放的关键。每个等待器实例在析构时自动调用取消等待方法。这确保了即使协程因异常或提前返回而未正常完成I/O操作，监听事件也能被正确清理。

从实现角度看，资源获取即初始化模式本质上是将资源释放责任从调用方转移到对象本身。调用方无需记住在各种退出路径上手动释放资源，这大大降低了资源泄漏的风险。

## 4.6 并发通信原语

在协程并发模型中，各协程的执行时机由事件循环决定，而非固定的调用栈顺序。这意味着协程间不能像线程间那样通过共享内存和锁进行通信——协程的执行顺序不确定，共享数据的竞争条件难以预测。因此，协程间需要一种通信机制来安全地交换数据。

常见的协程间通信模式有三种：回调模式将通信结果通过函数指针传递，但会导致代码碎片化；Future/Promise模式允许异步调用返回值，但不支持一对多的广播场景；Channel模式提供双向数据通道，发送方和接收方可以相互等待，适合生产者-消费者模式。本框架选择Channel作为协程间通信的原语，因为它既能保证数据安全传递，又能保持代码的线性可读性。

Channel的核心功能是充当协程间的有界缓冲区：一端协程发送数据，另一端协程接收数据。Channel支持两种模式：无缓冲模式要求发送和接收必须配对执行，发送者在接收者就绪前一直阻塞；有缓冲模式允许一定数量的数据暂存于队列中，发送者和接收者可以独立执行。本框架的实现中，缓冲容量在构造时指定，零表示无缓冲模式。

无缓冲Channel相当于容量为零的有缓冲Channel，其特点是数据的传递是同步的——发送操作必须等待接收操作完成才能完成。这适用于需要严格同步的场景，例如事件通知。有缓冲Channel则允许一定的异步性，数据先存入缓冲区，发送操作可以立即返回。

**同步机制**通过互斥锁保护Channel内部状态。当发送者发现有待接收的协程时，直接将数据传递给接收者而非存入队列——这避免了不必要的数据拷贝。当缓冲区有空闲空间时，数据直接入队。只有在既无等待接收者且缓冲区满的情况下，发送者才需要挂起。

这种设计在学术文献中称为"队列匹配"优化。其核心思想是：如果接收者已经在等待，那么直接传递数据比先存入队列再取出更高效。该优化减少了数据在缓冲区中的移动次数，降低了缓存失效的概率。

**协程唤醒机制**：Channel采用直接唤醒而非调度器唤醒的方式。当发送者或接收者需要等待时，会创建等待器并执行协程挂起；另一端操作完成时，直接调用恢复方法唤醒等待的协程，而非将协程加入事件循环的就绪队列。

这种设计的优势在于：首先，发送-接收本就是配对操作，两者之间是生产者和消费者的关系，当消费者唤醒生产者时，逻辑上是连贯的，直接唤醒保证了配对的原子性；其次，直接唤醒避免了调度开销，如果通过调度器唤醒，被挂起的协程需要等待下一轮事件循环才能恢复，而直接唤醒使得协程在另一端的调用链上立即恢复；第三，调度顺序是不确定的，如果唤醒依赖调度器，在某些场景下可能出现调度顺序导致的死锁，直接唤醒使得唤醒逻辑是确定性的；第四，直接恢复在接收者的调用栈上继续执行，发送者是接收者的延续，这种语义与函数调用类似，更符合程序员的直觉。

当然，直接唤醒也有潜在问题：如果发送者和接收者形成循环唤醒，调用栈会不断嵌套。但在本框架的应用场景中，Channel操作通常是单向的，不存在循环唤醒的情况。

**关闭语义**采用"发送禁止、接收延续"策略。Channel关闭后禁止新的发送操作，但已缓冲区中的数据仍可被接收；当缓冲区也清空后，接收操作将收到异常信号。这种设计使得发送方可以通知接收方"数据已发送完毕"，接收方可以优雅地处理正常结束和异常退出两种情况。

值得注意的是，关闭语义的选择并非唯一。有些实现采用"发送立即失败"策略，发送操作在关闭后立即返回错误而非挂起；有些采用"接收延续至缓冲区清空"策略，接收操作会等待所有数据被消费后才收到结束信号。本框架选择当前策略的原因是：关闭操作通常表示生产者不再产生新数据，消费者应该能够消费完缓冲区中的遗留数据后自然感知结束。

**设计权衡**：Channel采用互斥锁保护并发访问，这意味着多个协程不能同时调用同一个Channel的方法。理论上，无锁数据结构可能提供更高的并发性能，但在实际应用中，Channel的竞争程度通常不高——每个发送或接收操作持续时间很短，且大部分时间协程处于挂起状态而非占用锁。引入锁的简单实现更易正确实现和调试，也更容易与协程挂起机制配合。

另一个设计权衡是Channel的容量设置。容量过小会导致频繁的协程挂起，吞吐量下降；容量过大会增加内存占用，且数据在缓冲区中停留时间过长可能影响实时性。本框架允许用户根据具体场景调整容量，未设定默认值。

# 第五章 网络层的设计与实现

## 5.1 设计概述

网络层位于协程库之上、远程过程调用框架之下，负责封装底层套接字操作并将其协程化。本框架选择自行实现网络层而非依赖既有库（如libevent、boost.asio），原因在于：协程库需要与网络层深度集成以实现高效的I/O等待；既有异步网络库通常采用回调模型，与协程风格不匹配；自主实现可以针对远程过程调用场景进行专门优化。

网络层的设计遵循三个原则：透明的协程化使上层代码无需感知I/O等待机制；高效的I/O模型利用Linux的边缘触发epoll实现高并发连接处理；完善的资源管理确保套接字和缓冲区资源正确释放。

## 5.2 传输控制协议服务端封装

传输控制协议服务端封装类负责监听端口并接受客户端连接请求。

接受连接方法的实现采用循环等待策略：首先通过等待器注册读事件监听，此时协程挂起；监听套接字可读后协程恢复，调用accept系统接口获取客户端套接字；如果遇到非阻塞套接字特有的临时不可用错误码，继续注册监听等待下次机会；其他错误则抛出异常。

这种实现方式避免了为每个监听套接字分配独立线程的开销。在高并发服务器场景中，监听套接字的接受操作本身通常不是瓶颈，因此使用协程等待而非线程阻塞是合理的。

服务启动函数封装了地址解析、套接字创建、端口绑定和监听启动等操作。其中套接字创建时即设置为非阻塞模式并启用关闭时执行标志，前者便于与epoll配合，后者避免文件描述符泄漏风险。地址复用选项的设置使得服务器可以快速重启而不必等待TIME_WAIT状态结束。

## 5.3 传输控制协议流与数据缓冲

传输控制协议流封装已建立的连接套接字，提供协程化的读写接口。每个传输控制协议流维护读写缓冲区和套接字文件描述符。

**环形缓冲区**是读写缓冲区的实现基础。相比简单队列，环形缓冲区可以重复利用存储空间，避免反复的内存分配释放。当读索引接近缓冲区末尾时，将未读数据移动到起始位置，从而腾出空间写入新数据。

读写操作的实现值得深入讨论。读操作首先尝试从缓冲区取出数据；若缓冲区不足指定字节数，则持续从套接字读取直到满足需求或到达文件结束符。关键在于"持续读取"的实现：每次调用recv系统接口后，如果返回临时不可用错误，则挂起协程等待可读事件，而不是阻塞线程等待。

写操作同样采用非阻塞循环策略：将数据写入缓冲区后持续调用send系统接口发送；如果遇到临时不可用错误，则挂起等待可写事件。这种设计使得大量并发写操作可以高效共享网络带宽。

**协议消息读取方法**是本框架的特色设计，专门用于支持自定义协议的数据接收。方法首先确保缓冲区中包含完整的协议头（包含起始标志和消息长度字段），然后根据解析出的消息长度继续读取完整数据包。这种设计确保了应用层协议解析的正确性，避免了粘包和半包问题。

## 5.4 协程化输入输出模型

协程化I/O模型将传统的回调式或线程阻塞式网络编程转换为同步代码风格，同时保持异步执行的高效性。

从程序员视角看，协程化I/O的使用方式与同步I/O几乎相同：调用read方法等待数据返回，结果直接可用；调用write方法等待发送完成，无需关心底层事件通知。不同之处在于：同步I/O调用期间线程被阻塞，无法处理其他请求；协程化I/O调用期间协程被挂起，同一线程可以执行其他协程。

```

│                     协程化读写执行流程                               │
```

这种模型在服务器场景中的优势尤为明显：处理一千个并发连接，如果每个连接单独占用一个线程，栈空间消耗将非常可观；而如果每个连接使用一个协程，同一线程可以高效处理大量连接。

**边缘触发模式的选择**是实现高效I/O的关键。边缘触发只在状态变化时通知一次，要求程序持续操作直到返回特定错误码。本框架通过协程挂起恢复机制完美契合这一特性：当epoll返回可读事件时，协程被唤醒执行读操作；若一次recv无法处理所有数据，数据暂存于缓冲区，下次读取直接取用而不必再次触发监听事件。

## 5.5 连接管理与异常处理

连接管理涉及传输控制协议流的完整生命周期控制。

**资源获取即初始化模式**在流对象中的应用体现在析构函数自动调用关闭方法。当流对象销毁时，无论是因为作用域结束、异常还是显式移动，都确保套接字被正确关闭。这种设计避免了因忘记调用关闭方法而导致的资源泄漏。

**移动语义支持**确保流对象可以作为函数返回值安全使用。移动构造函数和移动赋值运算符通过转移套接字所有权实现资源的正确迁移。需要特别注意的是，被移动走的对象在析构时不会执行关闭操作——因为套接字文件描述符已经被转移。

**异常处理**在网络I/O过程中捕获各类系统错误并转换为标准异常抛出。常见的异常包括连接重置、套接字读写失败等。上层业务通过标准异常捕获机制统一处理这些错误。

**设计局限**：当前实现中，每个连接对应一个传输控制协议流对象，当连接数量非常多时，对象本身也占用一定内存。一种优化方案是使用对象池复用传输控制协议流，但增加了实现的复杂度。对于一般规模的分布式系统，当前的简单实现已经足够。

# 第六章 远程过程调用框架的设计与实现

## 6.1 协议设计

远程过程调用框架采用自定义的TinyPB协议进行数据传输。协议选择二进制格式而非文本格式（如JSON），原因在于：二进制格式的序列化效率更高、传输数据量更小，更适合高性能场景；同时自定义格式可以针对框架需求进行专门优化。

协议采用TLV（类型-长度-值）风格的可变长结构设计，包含起始标志、数据包长度、方法名、错误信息、协议缓冲区数据等字段。起始和结束标志用于边界识别；数据包长度字段使接收方能够精确解析完整消息；方法名采用protobuf的标准全名格式（如"UserService.GetUser"），便于通过反射机制调用；错误处理字段支持服务端返回详细的错误信息。

**协议设计的权衡**：TinyPB协议的缺点是紧耦合于本框架，客户端必须使用相同协议才能通信。相比之下，gRPC使用HTTP/2和Protocol Buffers作为传输层和序列化层，通用性更强。TinyPB的设计选择是为了最大化性能和简化实现，适合框架自用场景。如果需要对外开放接口，gRPC是更合适的选择。

## 6.2 服务端实现

远程过程调用服务提供者是框架的服务端核心组件。

**服务注册机制**基于protobuf框架的反射能力实现。开发者按照protobuf服务定义语言声明远程过程调用接口，框架在运行时获取服务的元数据（服务名、方法列表）并建立索引。这种设计的优势在于：声明式接口定义既是业务代码又是接口契约，避免了额外的配置文件或代码生成。

**请求分发机制**根据请求中的方法全名路由到对应的服务处理。分发器首先解析方法全名提取服务名和方法名，然后在注册表中查找对应服务实例，最后通过protobuf框架的反射机制调用相应方法。这种路由机制使得框架与业务逻辑完全解耦。

```
ALGORITHM: dispatch(request, response)
    response.msg_id ← request.msg_id
    response.method_name ← request.method_name
    
    IF NOT parseFullName(request.method_name, svc_name, method_name) THEN
        response.err_code ← 1
        RETURN
    END IF
    
    svc_info ← services[svc_name]
    IF svc_info = NULL THEN
        response.err_code ← 2
        RETURN
    END IF
    
    method_desc ← svc_info.FindMethod(method_name)
    IF method_desc = NULL THEN
        response.err_code ← 3
        RETURN
    END IF
    
    req_msg ← svc_info.CreateRequest(method_desc)
    IF NOT req_msg.ParseFrom(request.pb_data) THEN
        response.err_code ← 4
        RETURN
    END IF
    
    rsp_msg ← svc_info.CreateResponse(method_desc)
    svc_info.service.CallMethod(method_desc, req_msg, rsp_msg)
    
    IF rsp_msg.SerializeTo(response.pb_data) THEN
        response.err_code ← 0
    ELSE
        response.err_code ← 5
    END IF
END ALGORITHM
```

值得注意的是，当前实现采用同步调用模式：分发器直接调用服务方法，等待方法执行完毕后序列化响应。对于计算密集型服务方法，这可能导致工作协程长时间占用。改进方向是支持异步服务方法，让计算密集型操作也能释放协程执行权。

**多工作协程模型**采用生产者-消费者模式。主协程负责接受新连接并将连接对象发送到通道，多个工作协程从通道取出连接并处理请求。这种设计允许控制并发度，避免瞬时大量连接冲垮服务端。

Channel在服务端承担连接分发的职责。在实现中，主协程调用接受连接方法获取客户端连接后，通过Channel的发送操作将连接传递给工作协程；工作协程通过Channel的接收操作获取连接并处理请求。

```
┌─────────────────────────────────────────────────────────────┐
│                   服务端连接分发模型                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  accept()协程        Channel<TcpStream>        workers     │
│       │                   │                      │            │
│       │  send(stream)   │                      │            │
│       │────────────────→│                      │            │
│       │                 │                      │            │
│       │                 │        recv()        │            │
│       │                 │←─────────────────────│            │
│       │                 │                      │            │
│       │                 │                      │ handleClient│
│       │                 │                      │←───────────││
│       │                 │                      │            │
│       │  send(stream)   │                      │            │
│       │────────────────→│                      │            │
│       │                 │                      │            │
│       │                 │        recv()        │            │
│       │                 │←─────────────────────│            │
│       │                 │                      │            │
└─────────────────────────────────────────────────────────────┘
```

这种设计的优势在于：连接接受速度和连接处理速度可以不同——Channel作为缓冲区，吸收两者之间的速度差异；工作协程数量可配置，从而控制服务端并发处理能力；当某个连接处理耗时较长时，不会阻塞其他连接的处理。Channel容量设置为100，意味着最多可缓存100个未处理的连接，超出后将导致接受连接的操作挂起。

## 6.3 协程化客户端实现

远程过程调用通道实现protobuf框架的标准接口，支持同步和异步两种调用模式。

**请求通道**采用多生产者单消费者模型。多个协程可以同时发起远程过程调用请求，请求被封装为任务对象后发送到通道；单个工作协程负责从通道取出请求、发送数据、接收响应并回调通知。这种设计简化了连接管理，多个并发请求共享同一个网络连接。

Channel在客户端承担请求分发的职责。当调用者发起远程过程调用时，请求被封装后发送到请求通道；工作协程从通道顺序取出请求，依次执行发送、接收、解析操作。

```
┌─────────────────────────────────────────────────────────────┐
│                   客户端请求分发模型                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  调用者A              Channel<RpcRequest>      工作协程     │
│       │                   │                      │            │
│       │  send(request)   │                      │            │
│       │────────────────→│                      │            │
│       │                 │                      │            │
│  调用者B               │                      │            │
│       │  send(request)   │                      │            │
│       │────────────────→│                      │            │
│       │                 │                      │            │
│       │                 │        recv()        │            │
│       │                 │←─────────────────────│            │
│       │                 │                      │            │
│       │                 │                      │ send()     │
│       │                 │                      │─→ recv()   │
│       │                 │                      │            │
│       │                 │        recv()        │            │
│       │                 │←─────────────────────│            │
│       │                 │                      │            │
│       │                 │                      │ done.Run() │
│       │                 │                      │←─────────││
│       │                 │                      │            │
│       │                 │        recv()        │            │
│       │                 │←─────────────────────│            │
│       │                 │                      │            │
└─────────────────────────────────────────────────────────────┘
```

这种设计的优势在于：多个调用协程可以并发发起请求，无需等待前一个请求完成；请求的发送和接收由单一工作协程顺序处理，保证了单个连接上的请求有序性；调用协程通过回调函数获得结果通知，实现了非阻塞的异步调用体验。

**重连机制**确保连接的可靠性。当检测到连接断开时，工作协程自动尝试重新建立连接。重连采用指数退避策略：初始间隔一秒，每次失败后翻倍，最多重试三次。指数退避是处理暂时性故障（如网络抖动）的标准做法，避免频繁重连加剧网络负担。

**设计局限**：当前客户端不支持请求级别的超时控制，所有请求共享同一个超时时间配置。改进方案是为每个请求独立设置超时时间，这需要更精细的协程调度控制。

## 6.4 服务发现机制

服务发现使客户端能够动态获取服务端地址，无需硬编码配置。

本框架集成动物园管理员作为服务注册中心。服务端启动时连接到动物园管理员，创建服务路径节点和方法路径节点，使用临时节点类型；客户端启动时连接到动物园管理员，通过获取子节点列表获取可用地址。

**临时节点的选择**是关键设计决策。与持久节点相比，临时节点在会话断开时自动删除，这确保了客户端永远不会连接到已下线的服务端，避免了无效地址的清理问题。代价是服务端必须保持与动物园管理员的会话连接。

**设计权衡**：动物园管理员的引入增加了系统复杂度，需要额外部署和维护。如果系统规模较小、服务器地址相对固定，直接配置地址可能更简单。动物园管理员更适合大规模分布式系统或需要频繁扩缩容的场景。

## 6.5 错误处理与超时控制

远程过程调用框架需要处理多种异常场景。

**错误分类**采用三层设计：网络层错误包括连接失败、数据发送接收异常等；协议层错误包括序列化失败、协议解析错误等；业务层错误包括服务不存在、方法不存在、服务端业务异常等。三层错误统一映射为错误码和错误信息，通过控制器传递给调用方。

**超时控制**允许调用方为每个请求设置独立的超时时间。实现采用并发运行模式：同时启动实际任务协程和定时器协程，谁先完成谁生效；如果定时器先触发，自动取消任务协程并关闭连接。

```
┌─────────────────────────────────────────────────────────────┐
│                   超时控制执行流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│              wait_for(task, timeout)                        │
│                     │                                        │
│         ┌──────────┴──────────┐                            │
│         ▼                     ▼                              │
│   ┌─────────────┐      ┌─────────────┐                      │
│   │  RPC任务协程 │      │ 定时器协程  │                      │
│   │  发送请求   │      │ sleep(timeout)│                     │
│   │  等待响应   │      │              │                      │
│   └──────┬──────┘      └──────┬──────┘                      │
│          │                     │                              │
│          ▼                     ▼                              │
│   ┌─────────────┐      ┌─────────────┐                      │
│   │  响应到达   │      │  超时触发   │                      │
│   │  返回结果   │      │ 取消任务    │                      │
│   │             │      │ 关闭连接    │                      │
│   └──────┬──────┘      └──────┬──────┘                      │
│          │                     │                              │
└──────────┴─────────────────────┴──────────────────────────────┘
```

在实际实现中，超时控制通过协程等待超时的方法实现。该方法并发启动实际网络任务和定时器任务：网络任务负责与服务器通信，定时器任务负责计时；当网络任务先完成时，定时器被取消，正常返回结果；当定时器先触发时，网络任务被取消，连接被关闭，返回超时错误。

这种设计的优势在于：调用方可以为每个请求独立设置超时时间，不同重要程度的请求可以有不同的超时配置；超时机制与协程调度深度集成，无需为每个请求创建独立线程或定时器。

但也存在一个问题：任务协程被取消时可能已经占用了部分资源（如已发送请求），取消后服务端可能仍会处理该请求并返回响应。下次调用时如果恰好复用同一连接，可能收到前一个请求的遗留响应。严格的处理方案是为每个请求分配唯一标识符并做匹配验证。

## 6.6 完整调用流程

从客户端到服务端的完整远程过程调用流程涉及多个层次组件的协作。

调用发起时，客户端构造协议请求对象，序列化协议缓冲区数据后发送到请求通道。工作协程取出请求，编码协议数据后写入网络连接，同时注册写事件监听；写事件就绪后发送数据。发送完成后，工作协程注册读事件监听等待响应；读事件就绪后接收数据并解码。响应解析后，工作协程通过回调函数通知调用方。
